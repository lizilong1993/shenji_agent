# 情报「历史时点查询」最小方案（待决策，未实现）

TODOLIST §3 的阻塞项原文是「待明确需要复现的范围」。本文把这句话拆成两个互斥解释，
给出推荐口径、可验收的最小形态，以及各自的代价。**没有代码改动**，等这条口径被采纳后再实施。

## 1. 两种解释，只能选一种

| 解释 | 回答的问题 | 需要存什么 | 推荐 |
|---|---|---|---|
| A. 只读查询（**推荐**） | 「截至 T 时刻，我们**当时**掌握的是哪些情报？」 | 现有数据已够：每条记录都带 `event_time` 与 `ingest_time` | ✅ |
| B. 派生结果快照 | 「T 时刻的关联、汇聚、看板长什么样？」 | 需要把 `links` / `convergence` / `key_items` 连同算法版本冻结存档 | 暂不做 |

两者不是同一件事：A 是**筛选**，B 是**物化**。先做 A 就能支撑复盘与审计的绝大多数问题；
B 只在「算法改过、要证明当时结论怎么来的」时才必要，而那时更需要的是算法版本号而不是快照。

### 为什么 A 不需要新建仓库

现有三类数据都已经带时间戳，够做「当时存在」的判定：

- 自动情报：`intel/cache.py` 的 observation 同时存 `event_time` / `ingest_time`（`cache.py:96-97`）；
  `bundle.json` 的每条 observation 同样有这两个字段（`normalize.py` 各源都写）。
- 人工情报：`manual.py` 的条目有 `created_at` / `updated_at` / `revision`，撤销只是把 `status`
  改成 `revoked` 并保留原条目。**但状态历史不留档**：撤销后 `updated_at` 被覆盖，
  只存最后一次变更。所以能还原「T 时刻是否已录入」（`created_at <= T`），
  **不能还原「T 时刻是否 active」**——今天已撤销、T 时还生效的条目会被误判。
  这条是本方案的硬边界，见 §5。
- 源目录与人工关联：`sources.revision()` / `correlations.revision()` 只给当前值，
  T 时刻的**目录/关联本身**若也要还原，才需要 B 类的存档——这是 A 的明确边界，写在验收里。

## 2. 推荐口径（A）的三条判定

1. **存在性**用 `ingest_time <= T`：T 之后才入库的记录，T 时刻不可能被看到。这一条是防守性的，
   防止「迟到记录」污染历史视图。
2. **可见性**用 `event_time <= T`：事件发生在 T 之后的记录，即使已经入库也不算「当时掌握」。
   两条同时成立才算当时可见。
3. **缺 `ingest_time` 的旧记录**按「存在性未知」处理：写进返回的 `warnings`，默认**不纳入**
   历史视图，而不是乐观放行。旧缓存里确实有一批只写了 `event_time` 的记录。

## 3. 最小接口形态

`GET /api/intel/overview?case_id=...&as_of=2026-11-01T00:00:00Z`

- 不传 `as_of`：行为完全不变（同 revision 命中同一份缓存）。
- 传 `as_of`：只影响 `items` 的筛选；`links` / `convergence` 在筛选后的集合上重算一次，
  但要明确标注「这是按当时的记录重算的，不是当时算好的结论」。
- `as_of` 非法或晚于当前时间：返回 400，不静默改写成当前时间。
- 返回体新增 `as_of`、`as_of_applied: true`、`late_records_skipped: n`，让调用方知道
  这次是历史视图而不是当前视图。

**不做**：UI 入口（改 UI 按规则 4 另批）、`correlations` 的历史还原、算法版本存档。

## 4. 验收标准

1. 不传 `as_of` 时，返回体与改动前逐键一致（含 `revision` 计算方式不变）。
2. 构造三条记录（T 前入库+T 前发生、T 后入库+T 前发生、T 前入库+T 后发生），
   传 `as_of=T` 后只有第一条在 `items` 里，`late_records_skipped` 为 1。
3. 同一 `as_of` 连查两次结果一致（缓存键需包含 `as_of`，否则会拿到当前视图）。
4. 缺 `ingest_time` 的旧记录：不出现在历史视图，且 `warnings` 里点名条数。
5. 人工记录：`created_at <= T` 的条目出现在历史视图；**其状态按当前值呈现**
   并在返回体标注 `manual_status_not_historical: true`（状态历史不留档，见 §5）。
   若要求状态也还原，需先给 `manual.py` 加一条只追加的状态日志，属另立任务。

## 5. 风险

- 缓存键：`management.overview()` 的 `self._cache` 目前以 `(case_id, revision, 小时)` 为键，
  加 `as_of` 必须进键，否则会互相污染——这是本方案唯一的实现陷阱。
- `revision` 是当前值的哈希，历史视图下它不再代表「当时的状态」，前端若拿它做乐观锁会误判。
  返回体里应明确 `as_of_applied`，由调用方区分。
- 人工情报的状态不可回溯（§1 已核实的硬边界）。若复盘的结论依赖「当时某条人工情报是否已被撤销」，
  A 方案不够用，必须补状态日志；这时应重新评估是否需要 B 类快照，而不是给 A 打补丁。

## 6. 与既有工作的关系

- 「按采集时间投影」已经做过（影像资源侧，`as_of` 取区间末日），口径一致：**用时间戳筛选现有记录，
  不重建派生结果**。本方案沿用同一条原则，不引入第二套时间语义。
