# 多源情报接入与案例驱动三阶段流水线

本文说明情报源元数据、公开平台接入可行性和案例驱动的采集流程。目标是先广泛发现，
再清洗关联，而不是一开始就用关键词把潜在线索裁掉。

## 1. 情报源元数据

每个情报源在 `intel/sources.py` 中除来源标识外，还应说明：

- `summary`：一句话说明它是什么、主要提供什么信息；
- `features`：关键能力或限制（实时性、覆盖、分辨率、权限、许可）；
- `coverage`：空间覆盖；
- `access`：接入方式与门槛（是否需要 Key、是否官方、频率限制）；
- `domains`：可提供的情报域，用于案例筛选；
- `kind`：`auto` / `manual` / `rss` / `weather` / `social` / `web`。

内置源的首屏介绍由 `SOURCE_INFO` 预置；人工新增源在表单中直接填写上述字段。
搜索与筛选覆盖名称、简介、能力、覆盖范围和情报域，而不仅是来源 ID。

## 2. 公开平台接入可行性

| 平台 | 可用接口 | 能拿到什么 | 主要限制 | 建议 |
|---|---|---|---|---|
| RSS/Atom 新闻站 | 标准 RSS/Atom | 标题、摘要、链接、发布时间 | 站点可能随时改版；需遵守 robots/ToS；无全文 | 已实现通用连接器，按案例配置白名单源 |
| GDELT DOC 2.0 | HTTP JSON/GeoJSON | 全球新闻文章元数据、主题、地点、语气 | 约 5 秒 1 次查询；只有元数据；偶发 429 | 作为广度发现层，案例清理阶段再判相关性 |
| NewsAPI | REST `/v2/everything` | 关键词/来源/语言/日期检索的新闻元数据 | 需要 Key；免费开发档有限、生产需付费；缓存条款 | 可选补充，不作为唯一新闻源 |
| 微博 | 开放平台 OAuth 2.0 | 授权用户的主页/个人时间线、单条微博、评论 | 标准接口不含公共关键词搜索；高级/商业接口需申请；内容合规要求 | 仅接授权账号或合规数据服务；不抓取网页 |
| 微信公众号 | 公众平台服务端 API | 自有公众号的消息、素材、发布、留言 | 没有公开文章搜索接口；只能管理自有账号 | 通过人工录入或经授权的账号订阅；不接非官方爬虫 |
| RSSHub | 自托管 RSS 路由 | 微博用户/关键词、公众号、新闻站点等 RSS | AGPL-3.0；路由依赖上游页面，易失效；需评估平台条款 | 作为隔离的可选适配层，失败不影响主流程 |
| Mastodon | ActivityPub / 实例 API | 公共时间线、标签、账号动态 | 各实例限流和授权策略不同 | 可选开放社交源，按实例配置 |
| Bluesky | AT Protocol 公共 AppView | 公开帖子搜索、作者、时间 | 公共接口限流；内容审核差异 | 可选开放社交源 |
| Telegram | Bot API / MTProto | 机器人所在频道消息；公开频道需用户客户端 | Bot 无法读任意公开频道；MTProto 涉及账号与 ToS | 仅在合规审查后可选，默认不启用 |
| YouTube | Data API v3 | 视频搜索、元数据、评论 | 配额按单位计（搜索很贵），默认 1 万/天 | 可选视频线索源，需配额控制 |
| X/Twitter | 官方 API | 帖子搜索、用户时间线 | 付费档位和速率限制严格 | 暂不默认接入 |
| Reddit | OAuth API | 帖子/评论检索 | 付费档位、公共 JSON 限制 | 暂不默认接入 |

说明：上表是接入可行性判断，不代表已获得各平台授权。涉及用户内容、个人信息和
平台条款的源，必须先完成合规评估；系统默认只启用官方公开接口、RSS 和人工录入。

## 3. 案例驱动的三阶段流水线

入口：`POST /api/intel/collect`（测试模式）。案例有 profile 时由服务端 profile
决定 AOI、源集合、时间窗和关键词；只有没有 profile 的案例才使用请求中的 bbox。

### 第一阶段：广泛采集

- 按案例 bbox（含缓冲）和时间窗拉取所有启用源；
- `filter_observations=False`，不在采集层按关键词/国家裁剪；
- 保留原始响应归档、源状态、错误和计数；
- 无坐标的新闻以案例中心作为质心，并标记 `is_centroid`、降低置信度；
- 产出 `candidates.json`。

### 第二阶段：清洗与过滤

- 丢弃坐标/时间无效、明显越界的记录；
- 按 observation_id 和（标题 + 小时）去重；
- 对仍在范围内的记录计算相关性：关键词命中、领域匹配、来源置信度、地理精度；
- 相关性只打 `high/medium/low` 标签，不因“没有关键词”直接删除；
- 报告 `kept_without_keyword`，便于评估关键词过滤会漏掉多少线索；
- 产出清洗后的 `bundle.json`。

### 第三阶段：综合与分析

- 跨域/同地/主题关联，生成 `links`；
- 关键情报打分与理由（关键词、领域、置信度、关联、时效、人工优先）；
- 保留原始来源、证据字段和人工/自动优先级；
- 产出 `pipeline.json`，界面显示“广泛采集 → 清洗保留（无关键词保留）→ 关联/关键”。

## 4. 前端集成

- 选中案例后，`applyCaseHooks()` 调用 `IntelPanel.onCase(caseId, data)`；
- 面板打开期间也会轮询案例 ID，避免深链先于案例加载时错过自动采集；
- 面板先查 `overview.pipeline`，6 小时内不重复采集；
- 否则 POST `/api/intel/collect`，后台执行，轮询 `overview.pipeline` 与 `/api/intel/job`；
- 演示模式服务端拒绝写操作，界面保持只读；
- 情报源页显示简介、能力标签、覆盖与接入门槛。

## 5. 当前限制

- 中文社交媒体没有稳定的公开搜索 API，默认不接；RSSHub 仅作为可选、可隔离的适配层；
- GDELT 可能 429，FIRMS 需要 `FIRMS_MAP_KEY`，缺失时在源状态中报告而不是中断；
- 相关性目前是规则打分，尚未接入实体识别/语义模型；
- 新闻质心定位会降低置信度，不能当作精确坐标；
- 没有 profile 的案例需要请求显式提供 bbox；当前前端从案例数据未稳定取得 AOI，后续应为所有案例补 profile 或显式 aoi 字段。
- 自定义 RSS 仅允许 HTTPS 公网地址；DNS rebinding 的完整缓解仍需连接固定解析结果。
