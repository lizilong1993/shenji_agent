## 0. 结论摘要

先给出五条结论，后文展开论证。

1. **需要先纠正一个事实判断**：当前两个官方案例的航路**不是随机数生成**，而是 `engine/scenario.py` 中手工写死的航路点，再按恒定航速逐帧插值。真正“起点→终点直线插值”的是前端 `TS注册/自建TS`（`web/src/situation.js`）。不过，“编成模板化、空间分布简单、单位行为重复、态势缺少因果”这些判断是成立的：新增的 R11–R20、B07–B11 大量由既有航线平移派生，台海陆上兵力集中在安平一隅，中印只有 10 个平台且多数为环线巡逻。

2. **现有引擎的准确定位是“航路生成 + 三级态势推理”，不是“对战推演引擎”**。它能生成逐帧位置、按 OSM 路网约束陆上机动、计算 L1/L2/L3 态势与 22 类战术意图，但没有探测不确定性、交战裁决、毁伤/战损、弹药油料、目标控制权迁移、胜负判定，也没有“以本阶段结果为下一阶段输入”的步进循环。因此，**当前数据是一次性离线生成的完整时间线，前端只回放，不推进引擎**。

3. **按用户决策，引擎主体改为自研 `wargame_core`**：以庙算公开数据契约/行为为兼容规格，clean-room 实现陆战规则，并原生扩展海面/空中裁决；situation3d 负责地理映射、三维呈现与三级推理。新增“战役编排器 + 兵棋内核 + 事件模型”。数据契约采用**增量字段**（`schema: situation3d.campaign.v3`），旧字段与旧客户端保持兼容。详见 §3.4。

4. **两个案例应走两条不同的叙事结构**：
   - 台海：两栖登陆战役，海上航渡—换乘—抢滩—巩固—向内陆夺控，预设“红方达成战役目标”的虚构结局，但把**引擎独立裁决结果**与**演示脚本结局**并列展示。
   - 中印：高原对峙—前沿摩擦—局部交火—增援与后勤—脱离接触，预设“停火/僵局”结局，重点是高海拔、道路破碎、后勤脆弱、证据有限下的意图歧义。

5. **实施顺序**：按用户决策，先台海完整、再中印完整。但第一步不是直接写案例，而是**规格提取与陆战内核 MVP**：把庙算的公开数据契约、地图格式、state/judge_info 字段、移动/通视/射击/毁伤规则整理成可测试规格，先实现并验证陆战最小闭环，再扩展海空与案例内容。

## 1. 现状分析

### 1.1 系统架构与数据流

当前实际数据流如下：

```
engine/cases.py           案例注册表（目标子集、热点、机位、战区）
        │
engine/scenario.py        目标定义、航路点、热点框、登陆阶段、build_frames()
        │
engine/roads.py           OSM 路网加载、吸附、最短路、连通分量
        │
        ├── frames[]      逐帧位置/高度/航向/航速/沿航距离
        │
engine/inference.py       L1 目标级 / L2 编组级 / L3 区域级规则推理
engine/intent.py          22 类战术意图本体（规则）
engine/intent_predict.py  意图集合 CES（可选的模型链路，带 no-reentry 投影）
engine/brief.py           把逐帧推理压成可读简报
        │
scripts/gen_demo_trajectory.py
        │
web/data/situations/<case>.json   （core / inference 分片）
        │
server/serve.py → web/src/app.js → Cesium 回放
```

关键点：

- **生成是离线的、一次性的**。`build_dataset()` 一次生成 1441 帧（12 小时 × 30 秒），把位置、推理、意图、简报全部写进同一个 JSON。
- **前端不调用引擎**。`app.js` 只按 `state.tick` 取 `frames[state.tick]` 与 `inference_frames[state.tick]`，没有“下一步”或“推进一个阶段”的接口。
- **案例数据不进 Git**。`web/data/*.json` 被 `.gitignore` 覆盖，改动只在服务器/部署目录生效；代码仓库只保留生成器与静态资产。
- **服务端按 `part=core|inference` 分片**，说明已经有“大数据集拆片”的工程基础，可继续扩展为 `part=stage|events`。

### 1.2 两个案例的现状

| 维度 | 台海案例 `taiwan_landing` | 中印案例 `india_china_west` |
|---|---|---|
| 名称 | 登台作战（海陆空全要素） | 中印边境西段（拉达克） |
| 战区 | `taiwan_strait` | `india_china` |
| 目标数 | **31**（红 20 / 蓝 11） | **10**（红 5 / 蓝 5） |
| 域分布 | 红：海 8 / 陆 7 / 空 5；蓝：海 4 / 陆 4 / 空 3 | 红：陆 3 / 空 2；蓝：陆 3 / 空 2 |
| 热点 | 18 个（含 7 个港口/机场设施框） | 10 个（含 3 个机场框） |
| 阶段 | 6 段：集结装载、航渡、换乘编波、抢滩突击、巩固滩头、向内陆夺控 | **无阶段** |
| 时长 | 12 h，1441 帧，30 s/帧 | 同 |
| 陆上机动 | 安平登陆场附近，沿 OSM 路网路由 | 拉达克路网，52 个连通分量，部分单位不可跨区 |
| 结局 | 无结束条件、无胜负 | 无结束条件、无胜负 |
| 叙事 | 阶段标签固定按 tick 切换 | 长期对峙，无起承转合 |

#### 1.2.1 台海案例的具体问题

- **编成“看起来多、实际重复”**：R11 与 R01 同为 052D，R12 与 R02 同为 054A，R19/R20 是 R06/R07 的平移副本，B07–B11 也多为既有平台的平移。航线平移量刻意不同，但行为模式、速度、任务角色高度同质。
- **陆上兵力过度集中**：R09/R15/R16、B06/B09/B10 都在安平登陆场附近做小环线，导致“向内陆夺控”阶段没有真正的纵深推进，也没有道路节点/城镇/机场的争夺。
- **阶段是“时间标签”，不是“态势结果”**：`LANDING_PHASES` 的边界写死在 0/240/600/840/1080/1320 tick；单位并不会因为滩头未巩固、损失过大或路网被切断而改变阶段。`unit_phase` 只是给单位套一个“参与阶段上限”，不是状态机。
- **没有局部交互事件**：没有“蓝方预备队投入”“岸舰导弹齐射”“航道布雷”“电子干扰”“机场被压制”等可被时间轴定位的事件；`inference` 只根据距离和传感器覆盖算威胁，不产生事件。
- **没有战损与目标状态**：目标从第 0 帧到第 1440 帧一直存在，`alt/speed/heading` 连续，但没有 `strength/ammo/fuel/status`，无法表现被击中、受损、撤离、补给。
- **没有结局**：12 小时结束时只是播放停止，`inference_summary` 给出峰值等级，但没有“谁达成什么目标”。

#### 1.2.2 中印案例的具体问题

- **编成过小**：10 个平台不足以撑起“战役演示”，L2 编组只有“红:陆、红:空、蓝:陆、蓝:空”四个组，交互关系稀疏。
- **多数单位是环线巡逻**：H01、H04、H05、H06、H07、H08、H09、H10 都 `loop=True`，画面表现为几架飞机/几辆车绕圈，缺少“前沿摩擦—增援—脱离”的节拍。
- **没有阶段**：`build_dataset` 对 `india_china` 明确返回 `phases: []`，前端阶段栏为空；这是诚实的，但也意味着案例没有叙事骨架。
- **路网限制被回避**：因为拉达克 OSM 路网碎成 52 个分量（Leh 在 13、Chushul/Galwan 在 16、Depsang/DBO 在 43），新增陆上机动单位很难跨分量路由，所以编成扩充时只加了空中平台与阵地类。这个取舍合理，但结果是地面态势更单薄。
- **没有高海拔效应的表达**：目标有 `altitude_m`，但没有“高原功率降额、直升机升限、无人机续航、冬季后勤”对速度和可用性的影响；`H01` 的属性里写了“高原功率降额 ~30%”，但运动学没有体现。
- **没有中印战区的城区 AOI / 高分辨率影像保证**：`THEATRE_URBAN_AOI["india_china"] = []`，`fetch_base_imagery.py --theatre india_china` 虽已支持烘焙，但是否已部署需在服务器确认；否则低空会回落到战区粗层级。

#### 1.2.3 “随机生成”说法的来源

- 官方案例：`scenario.py` 的航路点是手工坐标，**无随机数**。
- 前端自建 TS：`situation.js` 的 `buildSituation()` 把每个目标按 `start → end` 线性插值，默认起点/终点围绕当前机位左右偏移，用户可增删目标；这是“快速搭建”，不是官方案例生成器。
- 如果看到的案例目标位置每次都不同，更可能是：
  - 使用了 `TS注册` 生成的自建 TS；
  - 或部署目录里的 `web/data/situations/*.json` 被另一版生成器覆盖；
  - 或早期演示版本与当前 `feat/3d-situation-cesium` 代码不一致。

**建议在实施前先确认线上部署的数据文件版本**，避免按错误基线设计。

### 1.4 主要问题归纳

把用户提出的六个方面逐条对应到代码事实：

1. **初始态势不够丰富**
   - 编成靠“平移复制”，类型集中在 10 个军标键；UAV/直升机/运输队分别复用了 `aew/fighter/armor` 图标，类型辨识度低。
   - 空间分布不均衡：台海陆上集中在安平，中印只有 10 个单位；热点与目标之间没有“为什么在这里”的地理依据。
   - OSM 只用了道路；军事设施、海岸线/水系、地形高程没有参与目标选址与任务设计。

2. **战役过程缺少起承转合**
   - 航路写死、阶段写死、单位不响应态势；没有“触发—反应—结果”的链条。
   - 没有局部事件（交火、侦察发现、补给中断、预备队投入、电子干扰），时间轴只是位置回放。
   - 中印案例连阶段都没有。

3. **没有真正调用推演引擎做“下一阶段”**
   - `build_dataset` 一次性生成全时间线；没有 `step()`、没有状态输入/输出、没有阶段间因果。
   - 现有 `inference` 是“对已知轨迹做评估”，不是“根据上一阶段结果生成下一阶段”。
   - 数据集没有区分“脚本设定”与“引擎计算”。

4. **多层级态势不完整**
   - L1/L2/L3 有，但缺少“战役级总览”和“目标级历史”。
   - 没有从战役→战术区域→单目标的 drill-down；热点表与目标面板之间没有联动。
   - 阶段只有台海有，且阶段栏只显示当前阶段，没有阶段列表/跳转/阶段摘要。

5. **动态可视化不足**
   - 时间轴是 0–1440 的线性滑块，没有阶段色带、事件标记、章节跳转。
   - 标绘是静态手工图元，不能随阶段出现/消失；无法由数据集驱动“主攻方向、登陆场、火力扇面、封锁区”。
   - 目标没有状态变化；没有受损、摧毁、撤离、增援的出现/消失。
   - `EventFeed` 有统一事件模型，但没有战役事件 UI，也没有与时间轴/地图联动。

6. **没有完整结局**
   - 没有结束条件、胜负判定、战果统计、结局说明。
   - 台海“我方获胜”没有实现；即使实现，也没有与引擎结果区分。
   - 没有任何“虚构演示”的界面免责声明。

7. **工程与数据约束**
   - 台海数据约 39.6 MB（既有记录），gzip 后约 1/20；再加事件/状态/标绘会继续增长。
   - 意图模型逐帧评分代价高：5 目标 × 1441 帧实测 1645 s；现用 `INTENT_PREDICT_STRIDE=8` + `INTENT_MAX_PREDICT_TICKS=40` 限流，意味着大量帧的意图集合是“沿用上一评分帧”。
   - 拉达克路网碎片化，陆上单位跨分量路由会失败；不能靠“多加点”解决。
   - 新增平台类型需要同时补军标 SVG、3D 模型、LOD 映射、`intent.ROLE_*` 映射，否则会出现“有目标但没图标/没意图”的静默降级。

## 2. 目标、边界与验收标准

### 2.1 目标

在不推翻现有架构的前提下，把两个案例从“固定航路回放”升级为“**有初始态势、有阶段推进、有局部事件、有状态变化、有结局**的虚构战役演示”，并让战役级、战术级、目标级三个层次都能看懂。

具体目标：

- 每个案例 5–7 个阶段，阶段之间有明确的进入/退出条件和状态继承。
- 每个案例 18–36 个合成目标，类型覆盖海/陆/空与侦察、打击、保障、指挥等角色；空间分布由 OSM 道路、设施、地形与任务逻辑决定，不是平移复制。
- 每个案例 ≥8 个可定位的局部事件，事件带时间、地点、参与方、效果、来源（脚本/引擎）。
- 每个案例有引擎裁决的结束状态与演示脚本设定的结局；两者并列，明确标注。
- 前端支持战役总览、阶段跳转、事件定位、目标状态历史、时间窗标绘。
- 现有 L1/L2/L3、意图集合、简报、图层管理、标绘、路网自检等能力保持可用。

### 2.2 边界与安全声明

- 所有单位、番号、参数、事件均为**合成/虚构**；不使用真实部队当前部署、真实作战计划或非公开数据。
- 真实地理名称（台湾海峡、拉达克等）只作为公开地理参照；目标位置由演示规则生成，不代表现实兵力位置。
- 装备型号可以保留“真实类别”（如驱逐舰、战斗机）以提升可视化辨识度，但**单位名称、呼号、编成、战损、结局均为虚构**；界面与数据中必须有 `provenance: "fictional_demo"` 与免责声明。
- 裁决参数是“演示用合成参数”，不追求现实杀伤概率；导出在 `wargame_core_model` 块中，便于审查与替换。
- 不把“红方获胜”包装成预测；结局区必须同时显示“引擎裁决”和“演示脚本”。

设计原则：

- **脚本负责“意图与条件”，引擎负责“结果与状态”**。脚本可以规定“第 2 阶段蓝方投入预备队”，但不能直接写“红方获胜”；胜负由 `wargame_core` 根据状态计算。
- **状态只在一个地方推进**：`CampaignState` 由编排器持有，阶段结束写入 `state_<stage>.json`；下一阶段只读这份状态，不重新随机生成。
- **所有随机性可复现**：使用 `seed = hash(campaign_id, stage_id, tick, actor, target)` 的确定性伪随机；同一 seed 重跑结果一致。
- **旧数据契约不破坏**：新增字段全部可选；旧客户端仍能读 `frames/targets/hotspots/inference_frames`。

### 3.3 状态连续性与阶段推进

#### 3.3.1 CampaignState

```python
@dataclass
class UnitState:
    target_id: str
    status: str          # ready / damaged / destroyed / withdrawn / reserve
    strength: float      # 0-100
    ammo: float          # 0-1
    fuel: float          # 0-1
    readiness: float     # 0-1
    pos_latlon: tuple    # (lat, lon)
    alt_m: float
    heading: float
    objective_id: str | None
    last_event: str | None

@dataclass
class CampaignState:
    tick: int
    stage_id: str
    units: dict[str, UnitState]
    control: dict[str, dict]   # objective_id -> owner/red/blue
    events: list[dict]
    reserves: list[str]
    score: dict[str, float]
```

#### 3.3.2 阶段循环

```python
state = initial_state(spec)
for stage in spec.stages:
    orders = resolve_orders(stage, state)       # 条件化任务：受损撤退、预备队投入、目标变更
    frames, events, state = wargame_core.step(state, orders, stage)  # 陆/海/空裁决
    inference = infer(frames, targets, hotspots)                     # 复用现有
    intent = derive(frames, targets)                                 # 复用现有
    dataset.add_stage(stage, frames, events, inference, intent, state)
    state = commit(state, events)
outcome = evaluate_outcome(state, spec)
```

关键约束：

- **禁止在阶段开始时重新随机化位置**。阶段 N+1 的初始位置取自阶段 N 的最后一帧；被摧毁/撤离的单位不出现；预备队按事件 tick 进入。
- **阶段边界是“状态条件”而不是“纯时间”**。可以保留“最晚结束 tick”作为兜底，但优先使用 `exit_conditions`，例如“登陆场控制权 ≥ 60 或红方损失 ≥ 阈值或时间到”。
- **脚本事件必须有前置条件与兜底**。例如“蓝方装甲营反击”要求该营 `status != destroyed` 且 `fuel > 0.2`；不满足时触发替代事件（“预备队未能投入，转入防御”），不能凭空让被摧毁的单位出现。
- **每个阶段结束写一份 `stage_state`**，既用于下一阶段，也用于前端“阶段摘要”和复盘。

#### 3.3.3 脚本与引擎的边界

| 内容 | 由谁决定 | 标注 |
|---|---|---|
| 初始编成、初始位置、任务意图 | 脚本（campaign spec） | `source: "script"` |
| 每阶段任务/航路 | 脚本 + 条件化改编 | `stage.mode ∈ {scripted, mixed, adjudicated, engine}` |
| 运动学位置 | `wargame_core` | `frame.source: "engine"` |
| 探测/交战/毁伤 | `wargame_core`（陆/海/空） | `event.source: "engine"` |
| 剧情事件（如“预备队投入”） | 脚本 | `event.source: "script"` |
| 胜负 | `wargame_core` 计算 + 脚本设定并列 | `outcome.engine/script` |

前端用不同颜色/标签显示“脚本事件”和“引擎裁决”，并在简报中写明“本案例为虚构演示”。

### 3.4 自研兵棋内核 `wargame_core`（兼容庙算契约 + 海空扩展）

> 按用户决策：不再依赖 `train_env` 闭源 wheel，也不对 `.so` 做反编译；以庙算的公开数据契约、公开规则文档和黑盒行为为规格，clean-room 实现陆战规则，并在同一内核中原生实现海面/空中裁决。

#### 3.4.0 为什么是 clean-room，而不是反编译

- `train_env` 是 cp310 manylinux 编译扩展，仓库内没有可读规则源码；反编译/复制闭源代码既不可维护，也可能违反许可。
- 可合法复用的“规格”包括：`docs/docs.md` 的算子/地图/动作/裁决字段说明、`land_wargame_sdk/Data/Data/scenarios/*.json` 的想定格式、`maps/*/basic.json`/`cost.pickle`/`see.npz` 的地图格式、`land_wargame_sdk/docs/observation_example.json` 的态势样例、`docs/裁决表格.xlsx` 的公开裁决表。
- 实施前请确认 SDK 许可允许“行为观察 + 兼容实现”；若不允许，退回到“只参考公开文档、不运行原 wheel 做对比”的方式。
- 结论：**逆向的是数据契约与可观察行为，不是二进制代码**；目标是“规则口径一致、结果可解释”，不承诺 bit-exact。

#### 3.4.1 P0 兼容规格（先产出，再写代码）

需要把以下内容整理成 `docs/wargame_core_spec.md`，每条都能被测试：

数据模型：

- 保留庙算兼容字段：`obj_id/color/type/sub_type/name/cur_hex/blood/max_blood/carry_weapon_ids/observe_distance/move_state/...`，便于复用现有想定与观察样例。
- 新增扩展字段：`domain ∈ land|air|sea`、`unit_type ∈ infantry|vehicle|aircraft|ship|submarine|fort|support`、`altitude_band`、`fuel`、`readiness`、`sensors[]`、`weapons[]`、`status`。
- 坐标：默认 `cur_hex = row*100+col` 兼容庙算；自研内核可额外支持 `hx/hy` 双字段，突破 100×100 限制（例如 256×256），但导出庙算格式时仍用四位数。

#### 3.4.3 海空原生扩展

- **海面**：新增地形 `sea/coast/port/channel`；舰船 `unit_type=ship`，潜艇 `submarine`；机动按航速/转向/编队；探测含雷达视距、超视距、电子侦察；交战含反舰、防空、反潜；补给含港口/海上补给；登陆含舰→艇→车→滩头换乘。
- **空中**：固定翼/直升机/无人机 `unit_type=aircraft`，`altitude_band` 低空/超低空/高空；空中机动不受地面代价约束；探测/被探测按高度层；防空导弹/高炮/空战；机场 sortie/补给。
- **联合交战矩阵**：明确“谁能探测谁、谁能打谁”（陆对陆/陆对空/空对地/舰对舰/舰对空/空对舰/潜对舰/舰对潜），避免出现“坦克打军舰”这类不真实交互。
- 因为内核是自研的，海空是**原生能力**，不再有 `external_shim`；`campaign.engine.capabilities` 可写 `land/air/sea: native`。

- 生成流程：

```
  -> cost.pickle（按机动模式）
  -> see.npz（按通视模式）
  -> scenario.json（operators/cities/landmarks/config）
```

- 坐标转换：WGS84 → 局部等距/墨卡托 → 六角 axial/offset → `row*100+col`；反向转换把内核状态写回经纬度。
- 校验：3–5 个地标往返误差 ≤ 1 hex；滩头/河谷/山口落在正确格；道路连通性与 OSM 一致。

#### 3.4.5 阶段推进与事件

```
campaign spec
  -> hexmap_builder (OSM/DEM -> basic/cost/see)
  -> scenario_builder (targets -> operators/cities/landmarks)
  -> wargame_core.engine.step(state, actions)  # 自研内核，Python 3.8 可跑
  -> state_exporter (state/judge_info -> frames/events/outcome)
  -> campaign orchestrator (阶段继承、脚本事件、结局并列)
```

- 运行环境：不再需要 Python 3.10 的独立服务；`wargame_core` 与 situation3d 同为 Python 3.8 标准库实现，构建脚本直接调用。
- 阶段步进：每个阶段一个 `step()` 循环；上一阶段结束状态（位置/血量/弹药/油料/控制点）直接作为下一阶段初始 `state`，保证连续性。
- 事件：`judge_info` 风格的事件日志 → `events[]`，`source: "engine"`；脚本事件仍由 campaign spec 产生。
- 确定性：`seed = hash(campaign_id, stage_id, tick, actor, target)`；同 seed 重跑一致；支持 `replay.jsonl`。

#### 3.4.6 胜负与脚本

- `outcome.engine`：`wargame_core` 根据最终状态计算（目标点控制、算子损失、弹药/油料、时间）。
- `outcome.script`：演示脚本设定；`match` 表示是否一致；不一致时前端并列显示，以引擎结果为主。
- 每个事件、每个阶段、每个结局都必须带 `source` / `mode`；数据集顶层 `campaign.engine.capabilities` 声明 `land/air/sea: native` 与 `real_geography: hex_adapter`。

#### 3.4.7 验证策略（决定项目成败）

- **规则单元测试**：每条规则（机动代价、通视、观察距离、直瞄/间瞄/引导、伤害、压制、弹药、疲劳、上下车、布雷、工事）至少一个用例。
- **兼容性测试**：选取 3–5 个公开想定（如 `1231.json`、`1930331196.json`、`2120131194.json`），用“公开文档口径”与“原 wheel 黑盒输出”做定性对比（移动耗时、通视判定、命中/伤害分布、胜负）；不要求 bit-exact，差异要记录并解释。
- **回归**：同一 seed 两次运行一致；同一想定在 100×100 与 256×256 下结果趋势一致。
- **内容验收**：两案例的阶段连续性、事件因果、结局可解释（见 §2.3）。
- 若许可不允许运行原 wheel 做对比，则只用公开文档 + 公开样例做 golden test，并在文档中注明“未做黑盒对比”。

#### 3.4.8 工作量与风险提示

自研一个可用的陆战内核 + 海空扩展，远大于“接一个 SDK”。建议按 MVP 迭代：

- 陆战 MVP：六角地图、机动、通视、直瞄、伤害、目标点、胜负（约 2–3 周）。
- 海空扩展：海上机动/反舰/反潜、空中高度/防空/空战、登陆换乘（约 2–3 周）。
- 战役内容与前端（另计）。

不要在第一版追求“全规则复刻”；先覆盖两案例实际用到的子集，再用测试逐步加规则。规则未覆盖的部分必须在数据里标注 `approximated: true`，不能假装已实现。

### 3.5 OSM 与地理数据的利用

#### 3.5.1 现有数据

| 数据 | 位置 | 覆盖 | 当前用途 |
|---|---|---|---|
| OSM 道路 | `engine/data/roads/{taiwan_strait,india_china}.json` | 两台海/中印 | 陆上路由 |
| OSM 军事设施 | `engine/data/vector/military.geojson` | 仅台海 bbox（115–125E, 18–29N），1861 点 | 仅 WFS 发布，未进案例 |
| 海底光缆 | `engine/data/vector/cables.geojson` | 台海 | 未进案例 |
| 影像 | `web/tiles/imagery` | 台海分级；中印需确认 | 底图 |
| DEM | `web/tiles/terrain` | 台海；中印需确认 | 地形 |
| 建筑 | WSF3D / 3D-GloBFP | 台海城区 AOI | 三维体块 |
| 3D Tiles | `web/tiles3d` | 台海部分 | 三维场景 |

#### 3.5.2 缺口

- **海岸线/水系/土地利用没有矢量数据**。台海登陆点选择目前靠手工坐标；无法自动判断“哪里是滩头、哪里是悬崖、哪里是港口”。
- **中印没有 vector/military 数据**；`fetch_vector.py` 的 `BBOX` 固定为台海。
- **DEM 没有进入引擎**；`altitude_m` 是目标高度，不是地形高程，无法做“高原对速度/升限的影响”。
- **军事设施只发布、不参与**；目标选址没有“靠近机场/港口/雷达站/仓库”的地理依据。

#### 3.5.3 建议补充

> 在自研内核路线下，OSM/DEM 有**两个用途**：一是生成六角地图（`basic/cost/see`，兼容庙算格式），二是给 situation3d 做三维呈现与目标选址。前者是新增的硬需求，后者沿用现有 `features_osm` 思路。

1. `tools/fetch_vector.py` 增加 `--theatre` 与按战区 bbox；新增 `coastline`、`water`、`landuse`（至少 `military`、`harbour`、`aerodrome`、`urban`）数据集。
2. 新增 `wargame/hexmap_builder.py`（见 §3.4.2）：把 OSM 道路/水系/居民地 + DEM 栅格化为六角格，生成 `basic.json`、`cost.pickle`、`see.npz`；这是“现实场景”能否成立的关键。
3. 新增 `engine/features_osm.py`：
   - 路网最近节点/边、道路等级、桥梁/隧道（如数据可得）；
   - 设施点空间索引（按 `kind` 查询最近港口/机场/雷达/仓库/营地）；
   - 海岸线/水系点在多边形内判断（用于滩头/渡口/河谷）；
   - DEM 采样（读取本地 Terrarium 瓦片，按经纬度取高程）。
4. 目标选址规则（`engine/placement.py` 或在 campaign spec 中声明）：
   - 防御方：沿道路节点/隘口/城镇纵深配置，保持 2–3 道防线；
   - 进攻方：在路网可达的集结地域，距目标 30–80 km，避免一开局就贴脸；
   - 登陆方：换乘海域在岸线外 10–20 km，滩头选择坡度/道路可达性较好的段落；
   - 空中：巡逻站位在己方传感器/防空掩护内，避免开局即被对方 SAM 覆盖；
   - 所有陆上机动单位在三维呈现/自研内核路径中必须通过 `roads.route_latlon()` 验证；跨分量时改用空中/阵地/短距越野并标注。
5. 中印：至少补齐 `india_china` 的战区影像/高程/设施；若无法补齐，案例要在数据里标注“粗粒度底图”，不要假装有高分辨率覆盖。

### 3.6 多层级态势展示

#### 3.6.1 战役级（Campaign）

回答“这一仗打到什么程度、下一阶段是什么”。

- **阶段带**：时间轴上方显示 5–7 个阶段色带，当前阶段高亮；点击跳转。
- **目标卡**：每个 objective 显示控制方、控制度、价值、当前争夺单位数；点击聚焦。
- **力量对比**：红/蓝总强度、各域强度、损失比、弹药/油料均值。
- **事件流**：按阶段分组，显示脚本/引擎标签；点击定位。
- **总览地图**：目标点、控制色、主要兵力群、当前阶段焦点框；鸟瞰图同步。
- **阶段摘要**：阶段结束弹出/侧栏显示“本阶段结果：损失、控制变化、关键事件、下一阶段”。

#### 3.6.2 战术级（Tactical）

回答“这个区域内发生了什么交互”。

- 点击 objective/事件/阶段焦点 → 相机飞到战术视角。
- 显示局部单位、传感器覆盖、武器射程、交战线、控制区、时间窗标绘（主攻箭头、登陆场、火力扇面、封锁区）。
- 事件标记：探测、交战、命中、补给、增援、撤离；点击看详情。
- 保留现有 L2 编组信息（质心、跨度、关系）与 L3 区域等级。

#### 3.6.3 目标级（Target）

回答“这个目标现在什么状态、经历了什么”。

- 目标面板增加：
  - 当前 `status/strength/ammo/fuel/readiness`；
  - 状态历史（用小型时间条显示 ready→damaged→destroyed/withdrawn）；
  - 事件历史（被谁探测、被谁攻击、何时受损、何时补给）；
  - 意图集合随时间的收缩（复用现有 CES 面板）；
  - 轨迹按阶段着色；当前阶段加粗。
- 支持“定位到该目标”“查看该目标事件”“跟随”。

#### 3.6.4 Drill-down 路径

```
战役阶段 → 目标点/热点 → 局部单位 → 单目标
   ↑______________________________________|
```

- 面包屑/返回按钮；不丢失当前 tick。
- 阶段跳转不重置用户图层开关；切案例才重置（现有 `resetElementState` 逻辑）。

### 3.7 动态可视化

#### 3.7.1 阶段化时间轴

- `footer` 的时间轴改为“阶段色带 + 事件刻度 + 滑块”三层：
  - 色带：每个阶段一个颜色，宽度按 tick 比例；
  - 事件刻度：关键事件用小三角/圆点标出，hover 显示摘要；
  - 滑块：保留现有拖动/播放/倍速/步进。
- 增加“上一阶段/下一阶段”按钮；可选“阶段结束自动暂停”。
- 时间轴上方显示当前阶段名、阶段进度、阶段剩余时间。

#### 3.7.2 事件流与地图联动

- 复用 `EventFeed` 的统一字段（time/level/source/object/content/raw），新增 `source: "campaign"` 与 `stage_id`。
- 事件面板支持按级别/来源/阶段/参与方筛选；点击事件：
  - `setTick(event.tick)`；
  - `selectTarget(actor)` 或 `focus(location)`；
  - 高亮事件标记。
- 事件标记作为独立图层 `situation.events`，可在图层面板开关。

#### 3.7.3 时间窗标绘

- `Plotting.add()` 增加可选 `fromTick/toTick/stageId`。
- `Plotting.setTime(tick)`：遍历标绘，按窗口显示/隐藏；手工标绘默认 `fromTick=0,toTick=Infinity`，行为不变。
- 数据集 `plots` 在案例加载时导入，归入 `plot.campaign` 等图层；用户仍可编辑/删除（会话内）。
- 标绘类型复用现有 24 类：`attack_arrow`（主攻）、`assembly_area`（集结地域）、`beachhead`/`zone`（登陆场）、`fan`（火力扇面）、`band`（走廊）、`line`（阶段线/分界线）。

#### 3.7.4 目标状态与增援/战损

- `status=damaged`：图标叠加黄色/橙色描边或降低不透明度；面板显示强度条。
- `status=destroyed`：图标变为“残骸/叉号”变体（新增符号），停止运动；轨迹保留；事件流可查。
- `status=withdrawn`：淡出/移出地图，保留列表项（灰色）。
- `status=reserve`：在阶段开始前不显示；事件触发后从集结点出现，带“增援”标签。
- 轨迹按阶段分段着色，当前阶段高亮；事件点叠加在轨迹上。

#### 3.7.5 镜头编排

- 每个阶段声明 `camera`；用户点击“阶段跳转”时飞向该机位。
- 可选“导调模式”：阶段开始自动飞行 + 事件聚焦；用户拖动/滚轮立即接管（复用现有 follow 的 suspend 逻辑）。
- 不要在每个 tick 强制改相机；只在该阶段第一次进入或用户点击时执行。

### 3.8 结局设计

- 数据集顶层 `outcome` 同时包含：
  - `engine`：`wargame_core` 根据最终状态计算；
  - `script`：演示脚本设定的结局（可为空）；
  - `match`：两者是否一致；
  - `disclaimer`：固定文案。
- 前端在时间轴末尾/阶段摘要/TS简报中显示：
  - “引擎裁决：红方达成 3/4 目标，蓝方损失 5 个单位，判定红方胜”；
  - “演示脚本：红方获胜（虚构设定）”；
  - 若 `match=false`：“演示脚本与引擎结果不一致，界面以引擎结果为主，脚本结局仅作剧情展示”。
- 台海：脚本设定红方获胜；引擎独立计算，若一致则显示一致，不一致则并列。
- 中印：脚本设定“停火/脱离接触”，引擎可能给出“双方均未达成决定性目标/僵局”；同样并列。
- 简报 `brief` 增加 `outcome_text` 与 `disclaimer`；禁止把脚本结局写成“预测”。

## 4. 两个案例的具体设计

### 4.1 台海案例：联合登陆战役演示

#### 4.1.1 主题与时空

- 主题：红方两栖编队在海空掩护下穿越海峡，在台南安平—高雄以北地段登陆，夺控登陆场、机场与港口接近地；蓝方以海上拦截、岸防火力、空中巡逻与机动预备队实施防御。

| S1 | 航渡与海上拦截 | 180–420（1.5–3.5h） | 海峡南段 | 蓝方水面编队拦截、岸舰导弹试射、电子干扰；2–4 次交战 | adjudicated | wargame_core 海/空 |
| S2 | 换乘编波 | 420–600（3.5–5h） | 安平外海 | 红方换乘、蓝方岸防火力/无人机侦察；脚本“蓝方预备队前推” | mixed | wargame_core 海/空/陆 |
| S3 | 抢滩突击 | 600–780（5–6.5h） | 安平滩头 | 两栖车上陆、直升机近距支援、蓝方滩头火力；登陆场控制权 | adjudicated | wargame_core 海/陆/空 |
| S4 | 巩固滩头/反突击 | 780–1020（6.5–8.5h） | 登陆场—台南 | 蓝方装甲营反击、红方第二梯队上陆、工兵破障 | mixed | wargame_core 陆/空 |
| S5 | 向内陆夺控 | 1020–1320（8.5–11h） | 台南—高雄 | 红方沿路推进、蓝方迟滞防御、机场/港口争夺 | adjudicated | wargame_core 陆/空 |

> 海/陆/空全部由 `wargame_core` 原生裁决；未实现的规则必须在数据里标注 `approximated: true`，不能伪装成已实现。

如果采用 10 h 版本，按比例压缩；阶段边界仍应以状态条件为主。

#### 4.1.5 局部事件示例

1. **EV-S1-01 蓝方预警机升空**（脚本）：蓝方 E-2K 从东部机场起飞，进入海峡东侧巡逻；红方电子战飞机开始干扰。
2. **EV-S1-02 岸舰导弹试射**（引擎）：蓝方岸舰导弹连对红方护航舰发射，命中/未命中由 `pk` 裁决；若命中，红方舰艇 `strength -15`，航速下降。
3. **EV-S1-03 海上拦截**（引擎）：蓝方护卫舰编队与红方护航群交战；双方各损失/受损；影响后续护航能力。
4. **EV-S2-01 换乘开始**（脚本）：红方两栖舰释放登陆艇/两栖车；蓝方无人机发现换乘海域。
5. **EV-S2-02 岸防火力压制**（引擎）：蓝方炮兵/岸防火力对换乘海域射击；红方登陆舰受损或被迫转移到备用换乘点。
6. **EV-S3-01 抢滩**（脚本+引擎）：两栖车分队上陆；蓝方滩头阵地交火；登陆场控制权从 blue → contested → red。
7. **EV-S4-01 蓝方预备队投入**（脚本，带前置条件）：若蓝方装甲营未被摧毁且油料 > 0.2，则从台南方向反击；否则触发“预备队无法投入”。
8. **EV-S5-01 机场争夺**（引擎）：红方装甲/机步抵达机场外围；蓝方守备队防御；控制权变化。
9. **EV-S6-01 结局**（引擎+脚本）：若红方控制登陆场+机场，输出红方胜；否则输出“未达成目标/僵持”。

#### 4.1.6 结局条件

- 红方胜：控制 `OBJ-BEACH` 且 `OBJ-AIRFIELD`，且蓝方地面强度总和 < 40%，或蓝方主动撤离。
- 蓝方胜：红方登陆场控制权 < 40% 且红方两栖/登陆舰损失 ≥ 50%，或红方在 S4 结束前未夺控登陆场。
- 僵持：时间到，双方均未满足条件。
- 演示脚本：设定红方胜；若引擎结果不同，显示不一致，以引擎结果为主，脚本结局仅作剧情。

#### 4.1.7 视觉重点

- 海上：航渡编队、护航队形、反舰导弹交战线、封锁区（band/zone）、传感器覆盖。
- 两栖：换乘海域（zone）、登陆场（beachhead zone）、抢滩箭头（attack_arrow）、滩头火力扇面（fan）。
- 空中：CAP 巡逻线、预警机轨道、电子干扰扇区、空中走廊。
- 地面：主攻/助攻箭头、阶段线、防御阵地、反突击箭头、目标点控制环。
- 时间轴：阶段色带 + 事件刻度；结局卡。

### 4.2 中印案例：高原对峙—局部交火—脱离接触

#### 4.2.1 主题与时空

- 主题：虚构的高原边境对峙。红方高原合成营在典角—楚舒勒方向集结，无人机侦察；蓝方以列城为后勤枢纽，沿公路前送，前沿哨所守备德普桑/DBO 走廊。一次前沿巡逻摩擦升级为炮兵/火箭炮交火，双方增援后在国际调停下脱离接触。
- 时间：虚构 D-2 至 D+2（96 h 可压缩为 12–16 h 演示；建议 12 h、30 s/帧、1441 帧，保持与台海同构）。
- 空间：加勒万河谷、班公湖、德普桑平地、典角、楚舒勒、诺玛、列城机场。
- 特点：高海拔（3500–4900 m）、路网破碎、后勤脆弱、空气稀薄、证据有限、意图歧义。

#### 4.2.2 编成建议（18–22 个目标）

红方（约 9–11）：

| 群组 | 单位 | 类型 | 说明 |
|---|---|---|---|
| 地面 | 高原合成营（装甲/机步/步兵）×2 | 地面 | 沿典角—楚舒勒道路机动 |
| 火力 | 炮兵营 ×1、远程火箭炮 ×1 | 地面火力 | 前沿压制/纵深打击 |
| 防空 | 中程防空 ×1（可选便携防空 ×1） | 地面防空 | 掩护集结/阵地 |
| 空中 | 战斗机 ×1 编队、无人机 ×1、直升机 ×1 | 空中 | 制空/侦察/运输 |
| 保障 | 运输队 ×1、工兵 ×1 | 保障 | 前沿补给/道路保障 |

> 编队按 1 个目标计：红方合计 10（含可选便携防空为 11）。

蓝方（约 9–11）：

| 群组 | 单位 | 类型 | 说明 |
|---|---|---|---|
| 地面 | 前沿哨所分队 ×2、步兵营 ×1、装甲分队 ×1（可选） | 地面 | 德普桑/DBO/楚舒勒防御 |
| 火力 | 山地炮兵 ×1 | 地面火力 | 前沿火力 |
| 防空 | 要地防空 ×1 | 地面防空 | 列城/诺玛 |
| 空中 | 战斗机 ×1 编队、无人机 ×1、运输机 ×1 | 空中 | CAP/侦察/补给 |
| 保障 | 运输队 ×1、工兵 ×1 | 保障 | 列城—诺玛—DBO 补给线 |

> 编队按 1 个目标计：蓝方合计 10（含可选装甲分队为 11）；两台计 20–22，落在 18–22 区间。

新增类型：步兵/机步、运输队、无人机、直升机、火箭炮、迫击炮、侦察分队、残骸符号。中印以地面为主，空中为辅；不要照搬台海的海空编成。

#### 4.2.3 目标点

| id | 名称 | 类型 | 价值 | 初始归属 | 说明 |
|---|---|---|---|---|---|
| OBJ-GALWAN | 加勒万河谷 | valley | 20 | contested | 前沿摩擦点 |
| OBJ-PANGONG | 班公湖 | lake | 20 | contested | 脱离接触区 |
| OBJ-DEPSANG | 德普桑平地 | plain | 25 | blue | 巡逻权争议 |
| OBJ-DBO | DBO 走廊 | pass | 20 | blue | 前沿补给走廊 |
| OBJ-DEMCHOK | 典角 | valley | 25 | red | 红方集结/前沿 |
| OBJ-CHUSHUL | 楚舒勒 | plain | 20 | blue | 前沿枢纽 |
| OBJ-NYOMA | 诺玛 | base | 15 | blue | 前进机场/集结 |
| OBJ-LEH | 列城 | base | 30 | blue | 战区后勤枢纽 |

#### 4.2.4 阶段设计（5 段）

| 阶段 | 名称 | tick（30s） | 焦点 | 主要事件 | 模式 | 引擎 |
|---|---|---|---|---|---|---|
| S0 | 对峙巡逻 | 0–240（0–2h） | 加勒万/班公湖 | 双方巡逻、无人机侦察、无线电警告；脚本“巡逻队相遇” | mixed | wargame_core 陆/空 |
| S1 | 前沿摩擦 | 240–480（2–4h） | 加勒万/典角 | 推搡/警告射击/工兵筑路；意图歧义 | mixed | wargame_core 陆/空 |
| S2 | 局部交火 | 480–780（4–6.5h） | 加勒万—楚舒勒 | 炮兵/火箭炮交火、无人机引导、防空拦截 | adjudicated | wargame_core 陆/空 |
| S3 | 增援与后勤 | 780–1080（6.5–9h） | 列城—诺玛—DBO | 蓝方运输队前送、红方拦截、双方增援 | adjudicated | wargame_core 陆/空 |
| S4 | 脱离接触 | 1080–1440（9–12h） | 全局 | 停火、后撤、缓冲区；输出僵局/停火 | mixed | wargame_core + 脚本 |

#### 4.2.5 局部事件示例

1. **EV-S0-01 巡逻队相遇**（脚本）：双方巡逻队在加勒万河谷相遇，距离 < 1 km；意图集合出现歧义（RECON vs HOLD vs PROBE）。
2. **EV-S0-02 无人机侦察**（引擎）：红方 UAV 发现蓝方运输队；蓝方防空雷达开机。
3. **EV-S1-01 警告射击**（脚本）：前沿摩擦升级；双方进入更高警戒；`intent` 出现 ASSERT/PROBE。
4. **EV-S2-01 炮兵交火**（引擎）：蓝方山地炮对红方集结地域射击；红方反炮兵雷达定位后反击；双方损失。
5. **EV-S2-02 防空拦截**（引擎）：红方防空对蓝方无人机/战机发射；命中/未命中。
6. **EV-S3-01 运输队前送**（脚本+引擎）：蓝方运输队沿列城—诺玛公路前送；红方远程火箭炮/无人机拦截；若被拦截，DBO 补给下降。
7. **EV-S3-02 增援到达**（脚本）：双方增援部队进入；若道路被切断，增援延迟或取消。
8. **EV-S4-01 停火**（脚本）：国际调停，双方停火；若引擎显示一方仍有进攻能力，标注“停火为脚本设定”。
9. **EV-S4-02 脱离接触**（引擎+脚本）：双方后撤到缓冲区；控制权冻结；输出“僵局/停火”。

#### 4.2.6 结局条件

- 红方胜：控制 `OBJ-DEMCHOK` 且 `OBJ-GALWAN`，蓝方地面强度 < 50%，且蓝方补给线被切断。
- 蓝方胜：守住 `OBJ-DEPSANG`/`OBJ-DBO`/`OBJ-CHUSHUL`，红方地面强度 < 50%，且红方无法维持前沿补给。
- 僵局/停火：时间到，双方均未达成；或脚本触发停火。
- 演示脚本：设定“停火/脱离接触”；引擎若给出不同结果，并列显示。

#### 4.2.7 视觉重点

- 高原：地形剖面/高程标注、山口/河谷、道路线、前沿哨所。
- 后勤：运输队沿公路的轨迹、补给半径、被拦截点、DBO 走廊。
- 火力：炮兵/火箭炮扇面、反炮兵雷达覆盖、无人机侦察轨道。
- 空中：CAP 巡逻线、运输机航线、直升机起降点。
- 意图：强调“证据不足时的歧义”——CES 集合不收敛、`AMBIGUOUS` 状态、缺失证据提示。
- 时间轴：阶段色带 + 事件刻度；结局卡“停火/僵局”。

| 维度 | 台海 | 中印 |

### 5.3 测试与验收

**引擎侧**

- `test_hexmap_alignment.py`：WGS84 → 六角格 → WGS84 的往返误差；3–5 个地标误差 ≤ 1 hex。
- `test_wargame_core_rules.py`：机动代价、通视、观察距离、直瞄/间瞄/引导、伤害、压制、弹药、上下车、布雷、工事逐项测试。
- `test_wargame_core_compat.py`：公开想定（1231/1930331196/2120131194 等）的定性对比：移动耗时、通视、命中/伤害分布、胜负；差异记录在 `wargame_core_spec.md`。
- `test_scenario_export.py`：campaign spec → `wargame_core` 想定的算子/城市/武器字段完整；未知字段有告警。
- `test_state_export.py`：`wargame_core` state/judge_info → frames/events 的映射完整；`blood=0` → `destroyed`；时间对齐。
- `test_campaign_continuity.py`：阶段 N 结束状态 == 阶段 N+1 开始状态；无事件消失/出现。
- `test_wargame_determinism.py`：同 seed / 同输入两次运行结果一致；不同 seed 结果在合理范围。
- `test_victory_conditions.py`：构造边界状态，验证红胜/蓝胜/僵局。
- `test_events.py`：每个事件字段完整；脚本事件前置条件不满足时有兜底。
- `road_selftest.py` / `intent_selftest.py` / `intent_set_selftest.py`：旧链路不回归。
- `test_dataset_schema.py`：v3 必填字段、兼容字段、`campaign.engine.capabilities`。

**前端侧**

- `campaign_selftest.py`：
  - 加载两个案例；阶段数量/名称正确；
  - 点击阶段跳转 tick 正确；
  - 事件列表可筛选、点击定位；
  - 目标面板显示状态历史；
  - 时间窗标绘在窗口内可见、窗口外隐藏；
  - 结局卡同时显示 engine/script。
- `plot_selftest.py`：手工标绘不受时间窗影响。
- `consistency_selftest.py`：新增图层“意图置上后场景真的变了”。
- `deeplink_selftest.py`：`?case=...&tick=...&panel=...` 仍可用。
- 截图：至少 3 个阶段 × 2 案例，检查战役/战术/目标三视角。
- `pageErrors=[]`。

**性能**

- 记录构建时间：每案例 ≤ 10 min（目标；视服务器而定）。
- 记录 JSON 大小/gzip：核心数据 ≤ 2 MB gzip（目标）。
- 浏览器：1.5 km/6 km 机位 FPS 不劣于当前基线；长任务数量不增加；堆内存不显著增加。
- 若超标：减少帧数、按阶段分片、意图评分降频。

### 5.4 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 规则复刻偏差 | 自研内核与庙算行为不一致，演示可信度受损 | P0 做规格与测试向量；P1 逐规则单测；公开想定定性对比；差异记录并标注 `approximated` |
| 许可/合规 | 兼容实现或行为观察可能受限 | 实施前确认 SDK 许可；不反编译、不复制代码；必要时只依据公开文档 |
| 工作量被低估 | 自研内核周期长 | 先做两案例实际用到的规则子集；MVP 迭代；P7 再扩规则 |
| 六角格分辨率 | 大范围战区分辨率不足 | 分战役 AOI（台南—高雄 1 km/hex、拉达克 4–5 km/hex）；自研内核可支持 256×256 |
| 海空交互复杂 | 交战矩阵/探测/高度层组合爆炸 | 先定义“谁能探测谁、谁能打谁”矩阵；按案例实际交互实现；单测覆盖 |
| 脚本与引擎结果冲突 | 叙事矛盾 | 条件化事件 + 兜底；`outcome.engine/script` 并列；以引擎为主 |
| 数据体积/构建时间 | 加载慢、构建失败 | 分片、减帧、意图评分降频、缓存中间状态 |
| 中印路网碎片 | 陆上单位无法路由 | 只用同分量路线；空中/阵地单位补充；必要时加“越野短距”并标注 |
| 中印影像/高程缺失 | 低空画面粗糙 | 先烘焙战区/热点；明确标注覆盖级别 |
| 新增图标/模型缺失 | 目标辨识度低/静默降级 | 先补 5 类关键图标；模型可选；`symbology.validate()` 拦截未知键 |
| 影响既有功能 | 回归 | 增量字段、feature flag、分支、自检、服务器备份 |
| 现实敏感性 | 合规风险 | 全部合成、虚构、免责声明、不输出现实部署/作战建议 |

## 8. 下一步

本文只做“现状分析 + 总体方案”，不写实现代码。鉴于已确认走“自研内核 + 海空扩展”路线，下一步必须先做 P0 规格提取与陆战 MVP，而不是直接写案例：

1. **确认许可与 clean-room 边界**：确认庙算 SDK 许可允许“行为观察 + 兼容实现”；明确不反编译 `.so`、不复制闭源代码；若许可不允许运行原 wheel 做对比，则只用公开文档 + 公开样例。
2. **规格提取**：把 `docs/docs.md` 的算子/地图/动作/裁决字段、`scenarios/*.json`、`basic.json`/`cost.pickle`/`see.npz`、`observation_example.json`、`docs/裁决表格.xlsx` 整理成 `wargame_core_spec.md`，每条规则配一个测试向量。
3. **陆战 MVP**：实现 `hexmap` + `movement` + `los` + `detection` + `combat`（直瞄/伤害/压制）+ `state`（目标点/胜负）；用 `1231.json` 等公开想定做定性对比（移动耗时、通视、命中/伤害、胜负）。
4. **地图生成**：取安平附近 50×50 hex（1 km/hex），从 OSM 道路 + DEM 生成 `basic/cost/see`，放 2 个地面单位、1 个空中单位，验证移动/观察/射击/状态导出；再验证 WGS84 ↔ 六角格往返误差 ≤ 1 hex。
5. **海空扩展原型**：`naval.py` 先做舰船机动 + 反舰 + 补给；`air.py` 先做固定翼/直升机/无人机高度层 + 防空；定义“谁能探测谁、谁能打谁”矩阵；用 3–5 个交战用例验证。
6. **冻结 `campaign.v3` schema** 与 `campaign.engine.capabilities` 字段；然后进入 P3/P4 内容与 P5 前端。
7. 在服务器上核对 `web/data/situations/*.json` 的实际版本与目标数，确认与本地代码一致。

如果 P1 发现某些规则无法从公开资料/行为观察中得到，或工作量明显超出预期，应缩小规则子集、在数据里标注 `approximated: true`，而不是硬做“全规则复刻”。

如果按推荐路径执行，最终交付的是：两套**虚构、可解释、可复现**的战役演示案例，具备丰富初始态势、连续阶段推演、战役/战术/目标三级视图、事件驱动的时间轴、明确的引擎结果与脚本结局区分，以及完整的自检与免责声明。
